# Transport Layer & MCP Gateway

How requests get into Substrate and responses get out. Covers all three transport modes, the stream format, request routing, and the standalone MCP gateway binary.

## Transport Modes

Selected at startup via CLI flags. Only one mode active per process.

### Combined WebSocket + MCP HTTP (default)

Single port (default 4444). WebSocket at `ws://localhost:4444` for JSON-RPC 2.0, MCP HTTP at `http://localhost:4444/mcp` for MCP Streamable HTTP. Requires the `mcp-gateway` feature flag. Uses `serve_combined()` from plexus-transport.

### WebSocket Only (`--no-mcp`)

Pure JSON-RPC 2.0 over WebSocket. Uses jsonrpsee server directly. No HTTP routes.

### Stdio (`--stdio`)

Line-delimited JSON-RPC over stdin/stdout. MCP-compatible for tool integration. Default log level: `substrate=warn,jsonrpsee=warn` to avoid trace noise on stderr.

## PlexusStreamItem Format

All RPC methods return streams of `PlexusStreamItem`:

```rust
enum PlexusStreamItem {
    Progress { message: String, percentage: Option<f32> },
    Data { content: Value, content_type: Option<String> },
    Error { message: String, recoverable: bool },
    Request { request_id: String, request_data: Value, timeout_ms: u64 },
    Done { metadata: StreamMetadata },
}
```

| Variant | Purpose |
|---------|---------|
| `Progress` | Real-time status updates |
| `Data` | Actual content payload |
| `Error` | Inline errors. `recoverable = true` means stream continues |
| `Request` | Bidirectional — server asks client a question |
| `Done` | Stream termination with metadata |

## Request Routing

Method format: `namespace.method` (e.g., `arbor.tree_create`).

1. `DynamicHub.route()` splits on first dot
2. Looks up activation by namespace in `HashMap`
3. Calls `activation.call(method, params)`
4. Activation returns `PlexusStream`
5. Stream piped to WebSocket subscription sink

For hub activations (Orcha, Solar): nested routing via `ChildRouter`.

- `orcha.pm.create` → Orcha → ChildRouter → Pm.create
- `solar.mercury.info` → Solar → ChildRouter → Mercury.info

## Hub-Level Subscriptions

| Method | Purpose |
|--------|---------|
| `substrate.call` | Route any method call, return stream |
| `substrate.hash` | Get plexus schema hash (cache invalidation) |
| `substrate.schema` | Get full plugin/method schemas |
| `substrate.respond` | Handle bidirectional responses |
| `_info` | Well-known endpoint: returns `{"backend": "substrate"}` |

## MCP Gateway Binary

Standalone binary at `src/bin/mcp_gateway.rs` for stable MCP HTTP access:

```
Claude Code <-> MCP HTTP Gateway <-> Plexus (WebSocket)
                   (port 4445)          (port 4444)
```

- Auto-reconnects to Plexus on disconnect (2s interval)
- Caches plugin schemas
- Converts Plexus schemas to MCP tools
- Streams progress/data/errors back to MCP client
- CLI flags: `--port`, `--plexus-url`, `--reconnect-interval`, `--test`

## Bidirectional Transport

The Interactive activation demonstrates server-initiated requests:

1. Server sends `PlexusStreamItem::Request` with `request_id`
2. Client responds via `substrate.respond(request_id, response_data)`
3. Server unblocks and continues stream

Over MCP: bidirectional requests sent as notifications with `type="request"`, responses via the `_plexus_respond` tool.

## MCP Session Persistence

`SqliteSessionManager` persists MCP sessions to SQLite:

- Tables: `mcp_sessions` (id, created_at, last_seen_at), `mcp_session_cache` (event replay)
- Sessions survive server restart — clients reconnect to same session
- Auto-cleanup: sessions older than 30 days deleted on startup

## Authentication

Optional bearer token via `--api-key` or `PLEXUS_API_KEY` env var.

- Applied at the transport level, before routing
- When set, all requests must include `Authorization: Bearer <token>`
- When unset, no authentication required (logs warning at startup)
