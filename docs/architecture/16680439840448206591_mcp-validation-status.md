# MCP Validation Status

This document tracks the current state of MCP (Model Context Protocol) compliance for Substrate.

## Test Infrastructure

### Rust Integration Tests

Located in `tests/mcp_validator.rs`, these tests orchestrate the Python mcp-validator against our MCP HTTP endpoint.

```bash
# Run full compliance test (reports results without failing)
cargo test --test mcp_validator test_mcp_http_compliance -- --ignored --nocapture

# Quick health check (init, initialized, tools/list)
cargo test --test mcp_validator test_mcp_server_starts -- --ignored --nocapture
```

The test infrastructure:
1. Builds the release binary (`cargo build --release`)
2. Starts substrate server on port 4445
3. Waits for TCP connection readiness (without sending MCP requests to avoid state pollution)
4. Runs the Python mcp-validator
5. Parses and reports results
6. Cleans up server process on drop

### Dependencies

- **mcp-validator**: Python CLI from https://github.com/Janix-ai/mcp-validator
- **reqwest**: Rust HTTP client (dev dependency with blocking feature)

Install mcp-validator:
```bash
cd /tmp
git clone https://github.com/Janix-ai/mcp-validator.git
cd mcp-validator
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Resolved Issues

### 1. ✅ Per-Session State Machine (Fixed)

**Problem**: The `McpInterface` had a single `McpStateMachine` that was shared across all HTTP requests.

**Solution Implemented** (`src/mcp/transport.rs`):
- Added `McpSession` struct with per-session state machine
- Added `McpHttpState` with `HashMap<SessionId, McpSession>` for session tracking
- Sessions created on `initialize`, looked up by `session_id` query param
- For HTTP transport, auto-transition to Ready after successful `initialize` (since HTTP is stateless and `notifications/initialized` is not always sent)

### 2. ✅ HTTP Status Code Mismatches (Fixed)

**Solution Implemented** (`src/mcp/transport.rs`):
- Custom `handle_mcp_post_raw` handler that parses raw JSON first
- Returns 400 for parse errors, batch requests, and invalid request structure
- Batch requests detected and rejected with "Batch requests are not supported" message

### 3. ✅ Missing Fields in tools/list Response (Fixed)

**Problem**: The 2025-06-18 spec requires `description` field on all tools.

**Solution Implemented** (`src/mcp/types.rs`, `src/mcp/schema.rs`):
- Changed `McpTool.description` from `Option<String>` to `String`
- Empty descriptions get default: `"{method} method from {namespace} activation"`

### 4. ✅ Ping Response Format (Fixed)

**Solution Implemented** (`src/mcp/interface.rs`):
```rust
"ping" => Ok(serde_json::json!({
    "timestamp": chrono::Utc::now().to_rfc3339()
})),
```

### 5. ✅ Invalid Session Handling (Fixed)

**Solution Implemented** (`src/mcp/transport.rs`):
- Unknown `session_id` returns HTTP 401 Unauthorized
- Missing `session_id` for non-initialize methods returns HTTP 400 Bad Request

## Remaining Issue

### Invalid Params HTTP Status (Debatable)

**Problem**: Validator expects HTTP 400 for `tools/call` with missing `name` field, but we return HTTP 200 with JSON-RPC error code -32602 in body.

**Our Behavior**: Standard JSON-RPC 2.0 - return 200 with error in body for application-level errors

**Validator Expectation**: Return 400 for invalid params

**Analysis**: This is an edge case interpretation. JSON-RPC 2.0 says to return 200 with error for method-level failures. The validator's stricter interpretation treats invalid params as a transport-level error.

**Current Status**: Accepted as minor discrepancy (6/7 tests pass)

## Protocol Version Differences

| Feature | 2024-11-05 | 2025-06-18 |
|---------|------------|------------|
| Protocol version in params | Required | Optional (use header) |
| Capabilities field name | `capabilities` | `clientCapabilities` |
| Batch requests | Allowed | Rejected with 400 |
| Ping result | Empty object | Includes timestamp |
| Tool description | Optional | Required |

All versions supported via:
- `protocolVersion` optional with default
- `alias = "clientCapabilities"` for capabilities

## Manual Testing

The core MCP workflow is functional:

```bash
# Start server
./target/release/substrate &

# Initialize
curl -X POST http://127.0.0.1:4445/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"clientInfo":{"name":"test","version":"1.0"},"protocolVersion":"2025-06-18"}}'

# Send initialized notification
curl -X POST http://127.0.0.1:4445/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized","params":{}}'

# List tools (34 available)
curl -X POST http://127.0.0.1:4445/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'

# Call a tool
curl -X POST http://127.0.0.1:4445/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"health.check","arguments":{}}}'
```
