# Substrate v0.2.8 — State of the System

Substrate is the reference Plexus RPC server. You write Rust methods with `#[hub_method]`, and you get self-describing, streaming RPC with zero boilerplate for schema generation or transport wiring.

It serves WebSocket (Plexus RPC) and MCP HTTP on the same port (default 4444), plus a stdio mode for embedding. Synapse provides schema-driven CLI access — it reads the schema at runtime and builds its own command structure.

Built on plexus-core v0.4.0 and plexus-macros v0.4.0.

## Boot Sequence

1. **Parse CLI args** — `--fg`, `--port`, `--stdio`, `--no-mcp`, `--api-key`, `--log-dir`
2. **Initialize logging** — Dual output: stderr + rotating daily files. 7-day retention, 100MB cap per file.
3. **`build_plexus_rpc()`** — Constructs the DynamicHub:
   - Initialize SQLite storage pools per activation
   - `Arc::new_cyclic` to inject `Weak<DynamicHub>` into activations that need parent context (Arbor, Cone, ClaudeCode)
   - Register all 16 activations (14 regular + 2 hub activations)
   - Compute plexus hash, run changelog startup check
   - Recover interrupted Orcha graphs
4. **Optionally daemonize** — unless `--fg` or `--stdio`
5. **Start transport** — Combined WebSocket + MCP HTTP server, or stdio

## Key Architectural Patterns

### Parent Context Injection via `Arc::new_cyclic`

Activations that need to call other activations store a `Weak<DynamicHub>`. The cyclic reference is set up during `build_plexus_rpc()` — the hub is constructed with a closure that receives a `Weak` to itself, which gets passed into child activations before the `Arc` is finalized.

### Handle System

Handles are type-erased cross-activation data references. An activation produces a handle (e.g., Arbor returns a conversation handle), and a consuming activation resolves it lazily. This decouples activations — they share references without sharing types.

### Streaming-First

Every RPC method returns a `PlexusStreamItem` stream. There is no request-response mode — single-value responses are just streams that yield one item and close. This means progress events, partial results, and cancellation work uniformly across all methods.

### DynamicHub Routing

The DynamicHub dispatches `namespace.method` calls to the appropriate `activation.call()`. Registration is flat — each activation claims a namespace, and the hub routes by prefix match.

### Hub Activations with `ChildRouter`

Hub activations support nested routing beyond two segments. Orcha routes `orcha.pm.create`, `orcha.pm.list`, etc. Solar routes `solar.mercury.info`, `solar.venus.info`. The hub activation's `ChildRouter` implementation handles the sub-dispatch.

## Storage

Per-activation SQLite databases live at `~/.plexus/substrate/activations/{name}/`.

9 activations use SQLite: Arbor, Cone, ClaudeCode, Loopback, Lattice, Orcha, Mustache, Changelog, plus MCP session storage.

Arbor's `ArborStorage` is shared — it gets passed into both Cone and ClaudeCode at init time, since both need to read and write conversation trees.

## Feature Flags

```toml
[features]
default = ["mcp-gateway", "transport-plexus"]
```

| Flag | Purpose |
|------|---------|
| `mcp-gateway` | Combined WebSocket + MCP HTTP on same port |
| `transport-plexus` | WebSocket Plexus RPC transport |
| `transport-http` | HTTP transport |
| `transport-mcp` | Standalone MCP transport |
